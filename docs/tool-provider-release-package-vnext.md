# CA Client Tools Provider Release Package — vNext design

**Status:** IMPLEMENTED in the v1.1.0 release. The canonical YAML now carries the public Tool contracts, the release builds `ca-client-tools_interface_<version>.zip` and the platform archives contain `provider.yaml` plus the identical `interface/` tree. The concrete implementation boundaries are recorded in §6. The Host consumer side remains [ca-agent-demo#241](https://github.com/odango-chan/ca-agent-demo/issues/241); this repository publishes and verifies the package, it does not implement the Host loader.

**Consumers:** [ca-skill-compiler v2.1.0](https://github.com/odango-chan/ca-skill-compiler/releases/tag/v2.1.0) at Skill build time; `ca-agent-demo` v0.5.0 Generic Tool Registry at Host startup and execution. **Implementation tracker:** [ca-agent-demo#241](https://github.com/odango-chan/ca-agent-demo/issues/241).

## 1. Architecture decision

**YAML-first authoring; publish once, consume twice.** The Go Provider owns exactly **one canonical Tool definition source**, extending the existing YAML `contracts/provider-bindings/v2/provider-bindings.yaml` instead of creating a second maintained `tools.yaml`. This source includes the public Callable ID, Schema references, Capability membership and Effect alongside private execution bindings. Standalone input/output schemas can be maintained as referenced `*.schema.yaml` **source assets**; they are not duplicate ToolCatalogs and are deterministically converted into the required Interface Package schema files. Release tooling deterministically emits:

1. **The Compiler interface** in its **existing, frozen** CA-SL Interface Package format: `connectionagent.io/interface-package/v1alpha1`, with `ToolCatalog` (the exact `connectionagent.io/toolcatalog/v1alpha4` payload), `CapabilityCatalog`, standalone JSON Schemas, and any required EvidenceDescriptor/other linked artifacts.
2. **The Host runtime binding**: a small, generated YAML file, `provider.yaml`, containing the launch protocol/argv, the immutable Interface Package reference/digest, and exact public Callable ID → private `backendOperationId` mappings. It **does not duplicate** the Tool Schema, Effect, Capability definitions or a second ToolCatalog.
3. **The Go executable** containing the implementation and the embedded private backend catalog. Its `initialize` identity/digest and `catalog` response must agree with the packaged runtime binding.

**YAML is the editable source and human-facing deployment format; JSON is generated only where the frozen Compiler interface requires it.** In particular, the existing Compiler `interface/package.json` must remain JSON. Its `capabilities.json` and any JSON Schema `.json` exports may also be generated JSON; those are not separately edited. These are two generated **views**, not two separately authored catalogs. A single generation/validation pipeline from one source is mandatory. The Go source can use its existing embedded `provider-bindings/v2` Catalog as the starting point, but it currently lacks complete public Tool contracts and must be extended. Hand-maintained copies in Python Host or a parallel release Schema directory are forbidden.

**No change to frozen Compiler contracts:** this proposal does *not* rename `interface/package.json` to `package.yaml` or require the compiler to parse new file formats. Generated `*.schema.json` remains JSON Schema; YAML-authored JSON Schema is allowed as an input to generation only where the existing supported schema dialect permits it. All generated bytes and digests are validated through the existing Compiler v2.1.0 conformance tests.

**OpenAPI is not a mandatory Tool interface format.** Existing 3GPP/OpenAMSM OpenAPI (3.0 or 3.1, as supplied by the interface owner) may be a *source* for HTTP request/response schemas and private Provider execution details. The generic compiler-visible interface is `ToolCatalog + JSON Schema` in the already released compiler dialect. A non-HTTP Tool must not be forced to invent HTTP paths or fake OpenAPI operations.

## 2. On-disk release contents

Per-platform archive (e.g. future Linux amd64; version/name are examples, not a release claim):

```text
ca-client-tools_<version>_linux_amd64/
  ca-client-tools
  provider.yaml
  interface/
    package.json                 # required frozen Compiler format; generated
    tool-catalog.yaml           # generated from canonical Go-owned YAML
    capabilities.json           # generated; no separate authoring source
    schemas/
      <public-input>.schema.json   # generated JSON Schema
      <public-output>.schema.json  # generated JSON Schema
    evidence-descriptors.yaml    # include only if the interface exports one
  README.md
  CHANGELOG.md

GitHub Release:
  ca-client-tools_<version>_linux_amd64.tar.gz
  ca-client-tools_<version>_linux_arm64.tar.gz
  ca-client-tools_<version>_windows_amd64.zip
  ca-client-tools_interface_<version>.zip   # OS-neutral Studio / Compiler dependency
  SHA256SUMS
```

All compiler-visible files, including any optional EvidenceDescriptor and transitive Schema dependencies, must be included in an immutable Interface Package snapshot and exported with the expected manifest file digests. **Do not require Compiler to execute the Go binary, contact a Provider process or fetch schemas over the network.**

For cross-package Schema dependencies, provide the exact external Interface Package snapshots and Dependency Lock to Compiler as separate inputs; do not copy dependent schemas into this package as unrecorded duplicates.

### Independent Interface Package ZIP (Skill Studio / Compiler)

**Required release asset:** `ca-client-tools_interface_<version>.zip` (same release tag; no OS/architecture suffix). This is the **exact same** Interface Package snapshot as each platform archive's `interface/` directory, *not* a second Studio-only ToolCatalog and not a bundle of executable code.

- The standalone ZIP has `package.json` **at the archive root**, followed by `tool-catalog.yaml`, `capabilities.json`, all referenced `schemas/` and optional `EvidenceDescriptor` files at their exact manifest-relative paths. No `provider.yaml`, Go binary, CLI examples, credentials, private execution binding Catalog or source checkout is required.
- Each generated interface file's **uncompressed bytes are identical** across the standalone ZIP and every platform archive's `interface/` tree, including `package.json`. The Interface Package snapshot digest and internal per-file hashes are identical regardless of archive wrapper; archive checksum is separate.
- Generate the Interface Package **once per tagged release** from the Go-owned canonical YAML Tool definitions, validate it, and then **copy the same output directory** into all platform staging trees while packaging the standalone ZIP. Do **not** rerun a platform-dependent generator or author a Studio-specific schema.
- The independent ZIP is **versioned and immutable**: `<version>` follows the Provider release tag without `v` for asset naming, while `package.json.version` is the explicit Interface Package version; do not assume they must be equal or rewrite snapshot IDs. Both identities and the package digest must be reported faithfully.
- Release workflow includes the standalone ZIP in `dist/SHA256SUMS`, GitHub Release upload glob and release tests. It rejects an absent Interface Package generator, missing export, malformed `$ref`, invalid package hashes or any mismatch between the standalone ZIP and platform archives. **Do not publish a partial release.**
- Do not confuse this future Compiler-linkable Interface Package with the existing nondeployable `openamsm-mas-compiler-contract-v0.3.0.zip` candidate. The old candidate cannot be silently relabeled as a valid linked dependency.

**Skill Studio imports/remote acquisition:** a user may select the standalone ZIP locally, or Studio may fetch that exact asset from a **pinned GitHub Release tag** and verify its published checksum and Interface Package digest. Studio must unpack safely (bounded size/count, no path traversal, no duplicate names), validate `package.json` + export/hash closure and persist an immutable dependency snapshot/lock under its existing dependency ownership. The UI displays ToolCatalog, Capability and Schema references **read-only**. Any transitive dependency package not included in this snapshot must be provided/pinned separately; no silent network fallback or invented Schema.

**Tracking:** [Publisher release automation #31](https://github.com/odango-chan/ca-client-tools/issues/31) and [Skill Studio importer #261](https://github.com/odango-chan/ca-skill-studio-demo/issues/261).

**Current Studio gap (as checked 2026-11-23):** `ca-skill-studio-demo` currently supports upload/pinned Git of a *single* ToolCatalog YAML/JSON through `contract-acquisition.mjs`; it does not yet import a full Interface Package ZIP or build the Compiler v2.1.0 exact dependency snapshot/lock from it. Studio acquisition support is a **separate implementation task**, not a claim that uploading this ZIP already works.

### Compiler interface (`interface/package.json`)

Use the **already implemented** `connectionagent.io/interface-package/v1alpha1`. Its manifest has `apiVersion`, `packageId`, `version`, `languageTarget=connectionagent.io/v1alpha5`, `publisher`, `dependencies[]`, `exports[]`, `files[]`. Export kinds are `CallableCatalog`, `Schema`, `CapabilityCatalog` and, when needed, `EvidenceDescriptor` / `IngressCatalog`. Actual file hashes and export IDs are generated and verified; the following is only an abbreviated structural sketch:

```json
{
  "apiVersion": "connectionagent.io/interface-package/v1alpha1",
  "packageId": "<stable-provider-interface-package-id>",
  "version": "<package-version>",
  "languageTarget": "connectionagent.io/v1alpha5",
  "publisher": "<published-identity>",
  "dependencies": [],
  "exports": [
    {"kind": "CallableCatalog", "id": "example.session.read", "path": "tool-catalog.yaml"},
    {"kind": "CapabilityCatalog", "id": "example.session-read", "path": "capabilities.json"},
    {"kind": "Schema", "id": "urn:example:session-read-input:v1", "path": "schemas/session-read-input.schema.json"},
    {"kind": "Schema", "id": "urn:example:session-read-output:v1", "path": "schemas/session-read-output.schema.json"}
  ],
  "files": ["<exact sha256 manifest entries for all non-package.json files>"]
}
```

The `files` placeholder above is not valid conformance data. Real generation must emit the exact `{path,sha256}` records, and export every member of any multi-operation ToolCatalog by precise ID. Publisher identity and exported owner must meet existing Compiler static linking rules.

### Tool definitions (`interface/tool-catalog.yaml`)

Reuse the frozen `connectionagent.io/toolcatalog/v1alpha4` DTO; do not introduce a custom parallel `tools[]` contract for the Compiler. An illustrative READ operation:

```yaml
apiVersion: connectionagent.io/toolcatalog/v1alpha4
kind: ToolCatalog
metadata:
  name: example-provider-tools
  owner: example-provider-owner
spec:
  contracts:
    - kind: operation
      id: example.session.read
      effect: READ
      ownerOutcomes: [SUCCEEDED, FAILED]
      inputSchema:
        $ref: urn:example:session-read-input:v1
      outputSchema:
        $ref: urn:example:session-read-output:v1
```

The `capabilities.json` file exports exact Capability-to-Callable membership. Its contents are separately listed in the **same** Interface Package manifest, but all are generated from the **same Go canonical Tool source**, not manually authored as another authority. Each referenced `$ref` must resolve within the compiler's declared direct-dependency and snapshot/lock rules.

The standalone schemas are JSON Schema using the **Compiler-supported dialect/subset**. OpenAPI `components.schemas` from 3GPP source documents may be converted into these standalone schemas, but the converter must preserve required properties, type/format constraints, references and identity, or fail rather than silently narrow/weaken. A valid OpenAPI 3.1 document alone does not establish valid CA-SL interface package or full dialect compatibility.

For MUTATION, the compiler's frozen ToolCatalog requires more than Effect: Outcome, receipt Schema, mutation/reconcile and any Evidence Descriptor fields must be present and statically valid. The release builder must not emit a fake success receipt or silently omit those contracts just to make a mutation compile. The released Provider still gates generic Mutation, and no MUTATION Tool is exported by the Interface Package.

### Host runtime binding (`provider.yaml`)

**Proposed small runtime binding format, not an implemented schema.** Contains **no duplicate** input/output schemas:

```yaml
apiVersion: ca.tool-provider-runtime-binding/v1
providerId: ca-client-tools.sbi
providerVersion: <binary-release-version>
protocol: ca-client-tools.provider/v2
backendCatalogDigest: sha256:<exact-embedded-catalog-digest>
transport:
  type: stdio
  argv: [./ca-client-tools, provider, serve]
interfacePackagePath: interface
interfaceSnapshotDigest: <sha256-of-exact-interface-package-snapshot>
bindings:
  - publicCallableId: example.session.read
    backendOperationId: openamsm.smf.mas.sc.query
```

Public and private IDs in the runtime example are illustrative; actual bindings must be generated with exact reviewed IDs and valid callable identities, not inferred by string concatenation or lowercasing.

`transport.argv` is **process startup**, not one CLI command per Tool invocation. No shell expansion or arbitrary path escape. Connection uses long-lived NDJSON over stdin/stdout. Host owns the selected local package path and process configuration; sensitive credentials and private Host invocation references never appear in the public Schema or ToolCatalog.

At startup Host parses the generated `provider.yaml` with strict YAML validation (duplicate keys/unknown fields rejected), then verifies the interface snapshot digest, Provider handshake identity/version and embedded catalog digest against the generated runtime binding, and calls existing Provider v2 `catalog` with the explicit private IDs already enumerated in `bindings[]`. **No new “list all” wire method is necessary** for discovery when the release package lists exact public/private IDs. Unsupported or not-configured Tool bindings stay unavailable; a Skill requiring them is NOT_READY.

## 3. Compiler and Host consume the same publication

```text
Go canonical Tool definitions + actual handlers
             |
        release generator
             |
     +-------+-----------------+
     |                         |
Interface Package           Runtime Binding + Binary
(tool-catalog.yaml,         (provider.yaml + Go executable)
 capability catalog,
 JSON Schemas, evidence)
     |                         |
Compiler + Interface Lock   CA Agent Host deployment
 (static Skill linking)      (Tool registration, READY)
     |                         |
     +----------+--------------+
                |
          Runtime execution
                |
       Go Provider v2 invoke
```

- **Compiler:** accepts CA-SL source, exact Interface Package snapshots and Dependency Lock (Development v1alpha1) or frozen v1alpha5 resolved dependencies. It does not load the executable, evaluate runtime availability or claim Production Qualification. `build-development` output is `NOT_ADMITTED` until separate Host admission.
- **Host:** reads only an operator-approved local extracted Provider package, uses its Interface Package's **same** ToolCatalog and Schema files for registration/runtime validation, and uses the runtime-binding sidecar to start and dispatch to the Provider. The Host does not re-author ToolCatalog/Capability data.
- **Skill selection and authorization:** a registered Tool does not grant an arbitrary Skill access. Exact compiled Skill requirements and the Host's existing Root-scoped authorization still gate the call. Schema mismatch, unavailable binding and unsupported Effect fail clearly and are repaired in the next Provider release.
- **Version pinning:** the Compiler artifact records the Interface Package identity/digest; the Host must load a matching installed package or refuse admission. No version solver, automatic download, Plugin manager, governance platform or duplicate catalog needed.

## 4. Acceptance gates before calling format implemented

1. Go generator emits `interface/package.json`, ToolCatalog, CapabilityCatalog, standalone schemas and `provider.yaml` deterministically **from the same canonical YAML source**. Hashes and cross-file IDs are consistent; no human-maintained duplicate artifacts.
2. Existing `ca-skill-compiler v2.1.0` **actually** links a synthetic Skill against the generated Interface Package and its exact Dependency Lock; verify expected callable/Schema/Capability export resolution and a negative broken `$ref` case. Do not call an OpenAPI parse smoke test equivalent.
3. The release archive includes the Go binary, both generated interface/runtime views, valid checksums; provider `initialize/catalog` agrees with `provider.yaml`. The **independent** `ca-client-tools_interface_<version>.zip` is auto-generated in the same tagged workflow, present in the GitHub Release and `SHA256SUMS`, and its uncompressed Interface Package bytes match each platform archive exactly.
4. The built Host wheel registers all selected available Tools **using the published package alone** and validates calls/outputs without Python MAS maps or manual `ToolImplementationCatalog` objects.
5. New Tool added to the Go-owned canonical YAML catalog and released + Skill recompiled → unchanged Host wheel loads it; missing Schema, duplicate ID, Effect mismatch or ungranted operation fail, not silently repaired.
6. Existing READ regression passes; Scheme C Mutation Create/Modify/Release requires an independently verified new Go Provider release with true Owner outcomes, private Run scopes and admission. Do not turn the READ-only public interface into an implied mutation-capable release.
7. Cleanly remove old Host-authored Tool catalogs/manual registration/MAS-specific Python adapters **at final Tool cutover** (ca-agent-demo#241); no lasting compatibility path.
8. Skill Studio independently imports the ZIP as a read-only locked Interface Package or fetches the exact pinned release asset; unsupported ZIP import must report unavailable rather than accidentally interpreting it as a single YAML ToolCatalog.

## 5. Non-goals

Not an OpenAPI-only interface, general-purpose schema registry, duplicate ToolCatalog, new Compiler API, runtime-capability trust authority, Plugin system, MCP transport, automatic installation platform or production-qualification proof.

## 6. Implemented boundaries (v1.1.0)

The format above is implemented with these exact, tested boundaries:

- **Canonical source.** `contracts/provider-bindings/v2/provider-bindings.yaml` now also declares `metadata.interface`, `spec.schemaFiles` and `spec.tools`. A Tool entry carries the public Callable ID, private `backendOperationId`, kind (`operation`/`observation`), Effect, Owner outcomes, Capability membership and Schema `$ref`s; a MUTATION entry must additionally carry `receiptSchema` and `mutation.commitProof`. `internal/catalog` validates all of it strictly, including that a Tool Effect equals its binding Effect and that every `$ref` names a declared source file.
- **Generator.** `internal/interfacepkg` and `cmd/ca-client-tools-release` emit `interface/package.json`, `interface/tool-catalog.yaml`, `interface/capabilities.json`, `interface/schemas/*.schema.json` and `provider.yaml`. JSON uses sorted keys and a fixed indentation, file lists are sorted, and the snapshot digest is the frozen `CA-SKILL-DEPENDENCY-SNAPSHOT` v1 framing. `verify` re-generates and byte-compares a staged package.
- **Published scope.** The Interface Package exports the eleven READ Tools (eight SMF context queries and three NF metrics lists), two Capabilities and four Schemas. **No MUTATION Tool is exported**: the Owner publishes no receipt/commit-proof/reconcile contract for a Provider mutation binding, so exporting one would require inventing the receipt. The typed MAS mutation callables remain Provider-runtime `Development` bindings and are documented as such, not silently qualified.
- **Provider manifest.** `provider.yaml` reports the Provider ID, the release version injected into the binary, `ca-client-tools.provider/v2`, the stdio argv, the interface path/snapshot digest, the extended backend catalog digest the running binary reports, and the exact public → private binding map. A process-level test starts the real binary and compares `initialize` identity/version/digest and the `catalog` response with `provider.yaml`.
- **Release workflow.** Generates the package once, runs the real `ca-skill-compiler v2.1.0` link gate (including a broken-`$ref` negative), stages the identical `interface/` tree into all three platform archives, publishes the standalone interface ZIP, verifies archive/ZIP identity and includes every asset in `SHA256SUMS`. The publish job then downloads the released assets and re-verifies the checksums.
- **Not implemented here.** Host-side package loading/registration is `ca-agent-demo#241`; Skill Studio ZIP import is `ca-skill-studio-demo#261`. This repository does not claim either. `BUILT` remains `NOT_ADMITTED`.

**Release boundary:** no tag, binary publish, SDK behavior or compiler compatibility claim without the exact generated assets and the compiler link gate.
